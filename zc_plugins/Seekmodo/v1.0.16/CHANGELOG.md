# Seekmodo Zen Cart connector — changelog

## v1.0.16
- **Per-shopper personalization plumbing (search-features-plan Sprint 5 PR 6).** Sprint 5 of the search features plan extended the gateway's LTR pipeline with per-shopper personalization — a personalized model that re-ranks search and recommendations for returning shoppers based on what they've clicked before. The gateway side landed in PRs 1-5 (resolver, feature appender, training, inference, privacy). v1.0.16 is the connector side: stamp the right shopper identity on every search / recommend / events call, honour the shopper's opt-out signal, and expose a "forget me" deeplink so the shopper-facing privacy surface is wired without a manual admin trip.

  Shopper identity, hybrid resolution:
  - `customer_id` — Zen Cart's `$_SESSION['customer_id']` when the shopper is logged in. Most durable; survives cross-session because it's literally the merchant's own customer id.
  - `shopper_pid` — value of a new first-party `sm_pid` cookie. Random 22-character URL-safe token (≈ 128 bits of entropy, base64url-encoded), minted on first visit by `numinix_seekmodo_resolve_pid()`, set with `SameSite=Lax` and `Secure` when the storefront is HTTPS. 1-year TTL by default. Never derived from PII — the cookie value is opaque, so even an attacker who steals it learns nothing about the shopper.
  - `session_id` — Zen Cart's PHP session id, used as the ephemeral last-resort fallback. Already plumbed through `_numinix_seekmodo_session_id()` for bot-check telemetry, so the gateway resolves it independently of the v1.0.16 changes.

  EU cookie-consent posture: the sm_pid cookie is gated behind `NUMINIX_SEEKMODO_PERSONALIZATION_COOKIE_ENABLED` (default **off**). Operators in jurisdictions that require explicit cookie consent can leave it off; the gateway falls back to session-id-only resolution and personalization simply doesn't activate for anonymous shoppers — no error path, no broken UX. Flipping it on (typically from admin.seekmodo.com → Personalization, which the RemoteConfig snapshot mirrors into the constant) starts minting the cookie on the next page view.

  Do-Not-Personalize:
  - Inbound `Do-Not-Personalize: 1` HTTP header is read by `numinix_seekmodo_do_not_personalize()` and forwarded verbatim to the gateway as `shopper_context.do_not_personalize=true`. The gateway-side `PersonalizationDecision` short-circuits BOTH reads (use base model, byte-equal to today's ranking) and writes (skip writing shopper history rows for this request) so an opted-out shopper never trains the personalized model and never sees a personalized result. Defensive resolver: any truthy value other than literal `0`/`false`/`off`/`no` counts as opted out (same posture as DNT).

  Forget me deeplink:
  - New `catalog/numinix_seekmodo_forget_me.php` endpoint accepts a `GET` (deeplink from the merchant's privacy page) or `POST` (form submission) and fires the gateway's `tenant.shopper.forget` MCP tool through the HMAC-signed Client. Resolves the current shopper's identity using the same precedence the search lib does, signs the call with the tenant's own HMAC secret (not the platform admin key — the merchant's storefront auth is what authorizes the erasure), and clears the local sm_pid cookie regardless of the gateway response so the shopper's browser stops carrying the id around immediately. The gateway records the erasure into the new `numinix_mcp_shopper_erasures` audit table for the merchant's compliance evidence.

  Plumbed surfaces:
  - `_numinix_seekmodo_build_search_payload()` attaches `shopper_context` to every `/v1/search` call.
  - `_numinix_seekmodo_typeahead_via_suggest()` attaches `shopper_context` to every `/v1/suggest` call (typeahead itself isn't personalized this sprint per the deferred-scope note in §6.5, but forwarding the context now lets the gateway stamp it into telemetry for the next sprint's personalized typeahead).
  - `catalog/numinix_seekmodo_recommend.php` attaches `shopper_context` to every `/v1/recommend.*` and `/v1/bundle.suggest` call. `PersonalizedRanker` on the gateway uses these to reorder recommendation candidates by shopper affinity.
  - `numinix_seekmodo_mirror_click()`, `numinix_seekmodo_mirror_impression()`, and `numinix_seekmodo_mirror_conversion()` all attach `shopper_context` to their `/v1/events` writes so the click / impression / add-to-cart / purchase telemetry rows carry the shopper identity for training-time joins.

  New `Client::callTool($name, $args)` method is the generic escape hatch for tenant-scoped admin-style tools the connector occasionally needs to fire — the forget-me deeplink uses it; we kept the per-tool wrappers (`search`, `events`, `recommend`, etc.) for everything on the hot path so each surface's metering + telemetry contract stays explicit in the SDK.

  No new metering. Personalization piggybacks on the parent search / recommend call's existing `Counter::incrementBilled()` per §6.5; the forget-me deeplink calls a non-metered admin tool. The connector adds zero new billable surfaces in v1.0.16.

## v1.0.15
- **Storefront recommendations + AI product bundles (Sprint 4 PR 6).** v1.0.14 brought typeahead via the gateway's SuggestTool; v1.0.15 brings the rest of the Sprint 4 recommendation engine to the Zen Cart storefront. The connector now ships everything needed to render `<div data-seekmodo-placement="pdp-related">` style widgets on the product detail, cart, home, and category pages — with the same fail-soft "render nothing if the gateway is unreachable" posture the rest of the connector uses, and no manual template hacks required.

  New pieces:
  - `Numinix\Seekmodo\Client::recommend($algorithm, $params)` — `POST /v1/recommend.{algorithm}` (or `/v1/bundle.suggest`). `$algorithm` is validated against an allowlist (`related`, `also_bought`, `also_viewed`, `trending`, `bundle.suggest`) before the call, so a typo can't accidentally hit an unintended path. Uses the search timeout and shares the breaker with the rest of the hot path; null on any failure (auth / transport / circuit-open / non-2xx / 402 `feature_not_in_plan` for tenants whose plan tier doesn't include recommendations or bundles).
  - `numinix_seekmodo_recommend($algorithm, $payload)` — function wrapper in `numinix_seekmodo_client.php`. Honours `numinix_seekmodo_is_locked_out()` so a dev/staging clone of a locked-domain tenant never accidentally hits the recommendation tools.
  - `catalog/numinix_seekmodo_recommend.php` — AJAX endpoint that the shipped JS module fetches. Reads `?placement=...&doc_id=...&limit=...` (plus `bundle_size` for bundle placements), validates the placement key against a fixed map (so a hostile client can't ask the storefront to render an arbitrary placement key), HMAC-signs the call server-side via the existing `Client::call` plumbing (the storefront JS never sees the tenant secret), and emits a flat `recommendations[]` array — bundle responses get flattened into the same shape so the JS doesn't have to branch on algorithm. Each successful call bills exactly one `searches` token on the gateway and lands in the `searches_recommend` display bucket; bots are excluded via the existing bot-check gate on the recommend.* surfaces.
  - `catalog/includes/templates/template_default/jscript/jscript_seekmodo_recommendations.js` — vanilla-DOM auto-attach module. On `DOMContentLoaded` it queries every `[data-seekmodo-placement]` node, fires one fetch per placeholder, and replaces the placeholder contents with a small `<ul>`-based product grid. Default heading text per placement is built in (operators override per-placement via `data-seekmodo-heading="..."` or hide it with `data-seekmodo-heading=""`). Bails silently when `fetch()` is unavailable; bails silently when the AJAX call fails. The page layout never shifts on a gateway hiccup because the placeholder div is already in the DOM at the right spot.
  - `NuminixSeekmodoObserver::onPageFooter` + `onShoppingCartHeader` — new notifier handlers for `NOTIFY_FOOTER_END`, `NOTIFY_HEADER_END_SHOPPING_CART`, and `NOTIFY_HEADER_END_INDEX`. The observer reads the active `main_page` (`product_info` → PDP placements, `index` → home or category placements depending on `cPath`, shopping cart header → cart-also-bought) and `echo`s the placeholder divs at the right spot in the page. No core template edits — same zero-touch contract as the search-result swap added in v1.0.9.
  - `NUMINIX_SEEKMODO_RECOMMENDATIONS_ENABLED` configuration key (default `false`). Operators flip the entire feature at once during a controlled rollout. The AJAX endpoint short-circuits when this is `false`, the observer skips the markup injection, and the JS module finds no placeholders to render — so a disabled tenant pays zero cost (no extra fetches, no extra DOM nodes).

  Per-tenant feature entitlement (Starter+ for `recommend.*`, Growth+ for `bundle.suggest`) is enforced gateway-side. A Hobby tenant flipping `NUMINIX_SEEKMODO_RECOMMENDATIONS_ENABLED=true` will see the placeholder divs render, but each fetch will return `ok:false, reason:gateway_failure` (gateway returns 402) and the slot will stay empty. Operators on Hobby see a clean fallback (no broken markup, no JS errors); operators on Starter+ see live recommendations as soon as the nightly co-occurrence rollup has at least one tick of telemetry to mine from.

## v1.0.14
- **Typeahead routes through the gateway's SuggestTool (Sprint 3 PR 6).** Up through v1.0.13 the connector's typeahead helper (`numinix_seekmodo_run_typeahead`) packed the shopper's prefix into a SearchTool payload and POSTed `/v1/search` with a slim `per_page=8` + `include_fields=products_id,name,model,price` shape. That worked, but it tagged every keystroke against the same `searches` master bucket the full SERP charges — typeahead UX on a busy storefront was indistinguishable from real search volume in the metering tables, and the connector couldn't price typeahead separately from search.

  v1.0.14 swaps the default path to the gateway's new `SuggestTool` (`/v1/suggest`, registered in Sprint 3 PR 3). The new path:
  - Returns three result blocks in one round-trip instead of just a flat hit list — `keywords` (top prior shopper searches matching the prefix, mined from the gateway's 90-day search-event telemetry), `products` (Typesense prefix-matched docs with the SuggestTool's commerce field set), and `categories` (top matching breadcrumbs from a Typesense facet query). The shipped JS renders all three as a three-section dropdown so shoppers can click a keyword or category suggestion to refine their query without leaving the box.
  - Meters against the new `searches_suggest` display bucket (via the dispatcher's `meta.surface_id='suggest'` wiring from Sprint 1 PR 0). The `searches` master bucket still ticks once per accepted call, but typeahead vs full-search volume is now separable in `numinix_mcp_usage_monthly`.
  - Honours the same bot-gate as `/v1/search` — scraper keystroke storms short-circuit to an empty envelope BEFORE the Typesense round-trip and write a `quota_skip` audit row. This was the most expensive surface to leave un-bot-gated; the old typeahead path was charging the master bucket for every scraper keystroke.
  - Falls back gracefully: if the gateway is older than Sprint 3 and `/v1/suggest` 404s, callers can flip `opts.use_search=true` (per-call) or `NUMINIX_SEEKMODO_TYPEAHEAD_USE_SEARCH=true` (global, via the same `_numinix_seekmodo_cfg` helper the rest of the connector uses) to force the legacy `/v1/search` path. The auto-fallthrough that an earlier draft of this PR shipped was removed because in shadow mode it would double-charge the tenant (one charge for the failed `/v1/suggest`, another for the fallback `/v1/search`).

  New connector pieces:
  - `Numinix\Seekmodo\Client::suggest($params)` — `POST /v1/suggest`. Uses the search timeout (typeahead is on the hot path); shares the breaker with `/v1/search` so a typeahead brown-out also degrades full search (intentional — both surfaces go to the same gateway, a brown-out on one is a brown-out on both).
  - `numinix_seekmodo_suggest($payload)` — function wrapper in `numinix_seekmodo_client.php` for callers that don't want to instantiate the Client themselves.
  - `_numinix_seekmodo_build_suggest_payload($q, $limit)` — in `numinix_seekmodo_search_lib.php` per the Sprint 3 PR 6 plan. Sits next to `_numinix_seekmodo_build_search_payload` so both payload builders stay in lock-step.
  - `_numinix_seekmodo_typeahead_via_suggest()` + `_numinix_seekmodo_typeahead_via_search()` — `numinix_seekmodo_run_typeahead` is now a thin dispatcher that picks between them. The suggest path adapts SuggestTool's three-block envelope into the helper's legacy `{q, items, total}` shape (so the v1.0.13 caller contract still works) and appends the two new arrays.
  - `catalog/numinix_seekmodo_suggest.php` — AJAX endpoint the shipped JS posts to. Returns `{ok:true, ...}` on enforce-path success or `{ok:false, fallback:true, reason:...}` on shadow / off / locked-out / failure so the JS knows to suppress its own dropdown and let the storefront's native typeahead render.
  - `catalog/includes/templates/template_default/jscript/jscript_seekmodo_typeahead.js` — 150ms-debounced keystroke handler that auto-attaches to `input[name="keyword"]`, `input#keyword`, or anything carrying `data-seekmodo-typeahead`. Vanilla DOM (no jQuery dep); silently no-ops on browsers without `fetch()`. Sites on a custom template need to copy this file into their own template's `jscript/` folder — Zen Cart doesn't auto-inherit jscript from `template_default`.

  Form-submit behaviour is intentionally unchanged: pressing Enter or clicking "Search" still POSTs to `advanced_search_result.php` and `numinix_seekmodo_run_search()` handles that path. Typeahead only augments the in-progress experience; the SERP is still the SERP.

## v1.0.13
- **Self-sufficient pairing (Sprint 15).** Up to v1.0.12 the pair-callback only persisted `tenant_id` + `shared_secret` and dropped a `/.well-known/mcp.json` discovery file. Everything else needed to make the storefront actually USE the gateway — flipping out of the default `off`/`shadow` mode, kicking off the initial catalog push, observing the storefront host so the locked-domain heuristic could fire — was a manual operator step (run `tools/install_numinix_connector.py`, manually flip `numinix_mcp_tenant_config.mode` in the gateway DB, run `numinix_seekmodo_push_catalog.php` from cron, etc.). Result on numinix.com / numinix.ca during the Sprint 14 cutover: both stores looked "connected" in the admin but search fell through to native Zen Cart LIKE indefinitely, no clicks were attributed, and the Typesense collections stayed empty.

  v1.0.13 closes that gap with a new `Pairing::activate_after_pair()` helper called from `numinix_seekmodo_pair_callback.php` immediately after `persist_credentials()`. Three things happen, all idempotent and all best-effort (a failure here logs but does NOT 4xx the pair):
  - **Local mode flip.** Writes `NUMINIX_SEEKMODO_MODE=enforce` and `NUMINIX_SEEKMODO_DEFAULT_MODE=enforce` so the next storefront request routes through the gateway. The gateway's `tenant.snapshot` write-through will overwrite this within 5 min anyway, but the local default avoids a "pair → 5 min of native search → suddenly enforce" surprise window.
  - **Initial catalog push (forked + detached).** Resolves a PHP binary (prefers `command -v php`, falls back to `/usr/bin/php` / `/opt/cpanel/ea-phpNN/...`) and shells out to `nohup setsid <php> numinix_seekmodo_push_catalog.php >> logs/numinix_seekmodo_indexer.log 2>&1 < /dev/null &` so the pusher detaches from the request and survives a php-fpm worker recycle. APCu-throttled to once per 6h so a paranoid double-pair doesn't queue two full reindexes. Windows hosts and `disable_functions=shell_exec` configs degrade to a no-op with the error reported in the activation report.
  - **Synthetic `tenant.snapshot` pull.** Forces a fresh (cache-bypass) GET against `/v1/tenant.snapshot` so the gateway's `Store::recordObservedDomain` records this storefront's host. The gateway's auto-default `locked_domain` heuristic in `Store::ensure` then picks that host as the lock on the very next snapshot pull (5 min later, or immediately if the merchant clicks "Refresh now" on the Connect admin page). No round-trip to the operator console required.

  The `numinix_seekmodo_pair_callback.php` response now carries an `activation: {mode_set, first_push_forked, snapshot_pulled, errors}` object so the seekmodo.com `/connect` page can show "Search live in 1-2 minutes" with a confidence indicator. Not load-bearing — the merchant's Connect dialog shows `ok: true` regardless.

- **Split search/index timeouts.** v1.0.10 → v1.0.12 had a single `NUMINIX_SEEKMODO_TIMEOUT_MS` (default 250ms) shared by `Client::search()`, `Client::index()`, and `Client::events()`. That made bulk catalog pushes basically uncompletable: a 500-doc Typesense upsert against a cold collection routinely takes 5-15s, the 250ms cURL timeout fired well before the gateway could respond, the connector recorded a circuit-breaker failure, and the next batch returned NULL. Operators ended up running the pusher with `HTTP_TIMEOUT_MS=30000` out of band (or via a wrapper script) which only worked because `RemoteConfig::pull` happened to skip on the CLI path's missing APCu — a fragile invariant.

  v1.0.13 splits the bucket. `Client.php` now carries two timeouts: `searchTimeoutMs` (default 1500ms, range 80-5000ms — used by `/v1/search` and `/v1/events`) and `indexTimeoutMs` (default 30000ms, range 1000-120000ms — used by `/v1/index`). Both are mirrored from the gateway via two new `tenant.snapshot` fields (`search_timeout_ms`, `index_timeout_ms`) and persisted in two new configuration rows (`NUMINIX_SEEKMODO_SEARCH_TIMEOUT_MS`, `NUMINIX_SEEKMODO_INDEX_TIMEOUT_MS`) by `RemoteConfig::writeThrough`. `fromConfiguration()` falls back to the legacy single-bucket `NUMINIX_SEEKMODO_TIMEOUT_MS` when the new ones aren't set, so a v1.0.13 connector talking to a stale-schema gateway still works (it just inherits the legacy 250ms search budget until the gateway-side migration runs).

  Connector-side floors and ceilings prevent operator misconfiguration: search clamped to 80-5000ms (anything more than 5s should already have fallen back to LIKE), index clamped to 1000-120000ms (Cloudflare's edge timeout is 100s — anything beyond that is wasted budget). The breaker's "absurdly slow success" rule (2× the configured timeout) now uses the per-call timeout, so an in-flight bulk index that happens to take 31s on a 30s budget no longer trips the search-side breaker.

## v1.0.12
- **Static `.well-known/mcp.json` writer (Sprint 14 PR 4 follow-up).** v1.0.11 shipped a PHP-driven interceptor for the `/.well-known/mcp.json` discovery URL via `init_numinix_seekmodo_well_known.php` at `autoLoadConfig[60]`. That interceptor only fires when Apache / nginx routes the request to PHP, which doesn't happen on stock cPanel / shared-hosting setups because (a) Apache's default config treats `.well-known/` like any other hidden dir and never forwards it to `index.php` without an explicit `.htaccess` rewrite, and (b) many Zen Cart installs live in a `/catalog/` subdirectory while the well-known URL has to be at site root — a root-level redirect to `/catalog/` catches the discovery URL before it can reach Zen Cart at all. **Symptom seen on production:** `https://www.numinix.com/.well-known/mcp.json` returned 404 (no rewrite); `https://redlinestands.com/.well-known/mcp.json` redirected to `/catalog/` (Zen Cart in subdir + root redirect). v1.0.12 fixes both by dropping a real static file on disk at every viable target directory:
  - `DIR_FS_CATALOG/.well-known/mcp.json` (always — Zen Cart owns this dir, write is guaranteed).
  - `$_SERVER['DOCUMENT_ROOT']/.well-known/mcp.json` (when set AND distinct from `DIR_FS_CATALOG` — this is the subdir-install case; covers redlinestands.com).
  - Fallback `dirname(DIR_FS_CATALOG)/.well-known/mcp.json` when `$_SERVER['DOCUMENT_ROOT']` is empty (CLI / certain FPM setups) AND the parent is writeable + distinct + not a disk-root path.

  A sibling `.htaccess` is dropped inside `.well-known/` with `Require all granted` + `Allow from all` to force-allow the file on shared hosts whose global `<Directory ~ "/\.">` deny would otherwise block it. The writer is fully idempotent — every write is conditional on the on-disk content not matching the canonical payload, so re-running on every snapshot poll is effectively free.

  Trigger points (in order of when the file first appears after install):
  - `numinix_seekmodo_pair_callback.php` — runs immediately after a successful pair. The pair response now carries a `well_known_mcp_json: [{path, status, detail?}, …]` array so the seekmodo.com side of the Connect dialog can surface partial-success / failure to the merchant.
  - `RemoteConfig::writeThrough()` — runs on every `tenant.snapshot` pull and push. Refreshes the file if the tenant id / gateway URL ever change.
  - `NuminixSeekmodoMcpDiscoveryObserver` — opportunistic refresh once per hour per FPM worker (APCu-gated; falls through to 1-in-100 sampling when APCu is missing). Lets an existing v1.0.10/v1.0.11 install that upgrades to v1.0.12 self-heal on the next storefront page render, without waiting for the merchant to re-pair or for the next snapshot poll.

  Failure posture is "report, don't bubble" — every code path is wrapped in try/catch, the writer NEVER throws to its caller, and an empty / failed write does NOT block pairing or 500 a storefront page. The v1.0.11 PHP interceptor stays in place as a secondary fallback for sites that DO have the `.htaccess` rewrite (or run Zen Cart at site root with a normal `.htaccess`); the `<link rel="mcp-server">` head tag continues to be the always-on discovery primitive that works regardless of file-system layout.

## v1.0.11
- **Public-MCP (anonymous-tier) discovery (Sprint 14 PR 4).** Two new discovery surfaces let third-party AI agents (ChatGPT, Claude Desktop, Cursor, etc.) find this storefront's product-search MCP endpoint at `https://<tenant_id>.mcp.seekmodo.com/mcp` without merchant intervention:
  - **`/.well-known/mcp.json`** — new early-init script `catalog/includes/init_includes/init_numinix_seekmodo_well_known.php` registered at `autoLoadConfig[60]` (BEFORE the connector's main boot at 80, well before sessions / templates / the messageStack init). When `REQUEST_URI` matches `/.well-known/mcp.json` the script renders a small JSON discovery document (`endpoints[]`, `tools`, `tenant_id`, `rate_limits`, `docs`) and `exit;`s. CORS is wide-open (`Access-Control-Allow-Origin: *`) because the doc is public information by design. Cache-Control is `public, max-age=3600, stale-while-revalidate=86400` so the edge can serve it for an hour. Tenant id + gateway host are read directly from the `configuration` table via a raw `mysqli` query so the interceptor stays self-contained — no dependency on the procedural boot file. **Routing prerequisite:** for the interceptor to fire, the catalog `.htaccess` must rewrite the path to `index.php`: `RewriteRule ^\.well-known/mcp\.json$ index.php [L,QSA]`. Operators who can't or won't edit `.htaccess` are still covered by the `<link rel="mcp-server">` head tag (below), which is the more widely-supported discovery primitive anyway.
  - **`<link rel="mcp-server">` + `<meta name="mcp-server">` head injection** — new observer `catalog/includes/classes/observers/NuminixSeekmodoMcpDiscoveryObserver.php` hooks `NOTIFY_HTML_HEAD_END` (fired from `tpl_main_page.php` inside `<head>`) on every storefront page and `echo`s two short tags advertising the same `https://<tenant_id>.mcp.seekmodo.com/mcp` endpoint. The `<link>` tag also carries a `data-discovery` attribute pointing at `/.well-known/mcp.json` so crawlers that prefer the formal discovery doc can find it. Per-request memoised — the build is amortised across multiple notifier hits on the same render. Conditions for emission: `numinix_seekmodo_enabled()` returns true (connector paired, mode != off, no domain lockout) AND a tenant id resolves; either false → no tag (the discovery surface goes away cleanly when the connector goes off, which is the right answer because the gateway's anonymous resolver would 404 the host anyway).
  - **Failure posture matches the hot-path observer.** Both surfaces wrap everything in `try/catch`. A discovery-endpoint failure NEVER 500s a storefront page — `.well-known` falls through to the normal index render (which 404s the path), and the head injector silently skips the tag.
  - **Auto-loader wiring.** `catalog/includes/auto_loaders/config.numinix_seekmodo.php` adds slot 60 for the well-known init script and a second `class` + `classInstantiate` pair at slot 200 for the head-injecting observer. The existing slot-80 boot and slot-200 hot-path observer are unchanged.

## v1.0.10
- **Standalone catalog pusher (Sprint 13 follow-up).** New `catalog/numinix_seekmodo_push_catalog.php` walks `TABLE_PRODUCTS` joined with `TABLE_PRODUCTS_DESCRIPTION`, `TABLE_MANUFACTURERS`, `TABLE_PRODUCTS_TO_CATEGORIES`, and `TABLE_CATEGORIES_DESCRIPTION` in 500-doc batches and pushes them through the existing `numinix_seekmodo_run_bulk_upsert($batch, $collection)` swap-point. Up to v1.0.9 the connector's indexer side was a swap-point only — it expected a pre-existing storefront-side Typesense indexer cron to splice into (the way Redline's `transfer_products.php` does). Plain Zen Cart 1.5/2.0 storefronts (numinix.com, numinix.ca, any out-of-the-box install) had no such cron, so the connector paired and started talking to the gateway but the per-tenant Typesense collection stayed empty, every `/v1/search` returned zero hits, the v1.0.9 observer fell through to native LIKE, and no impressions / clicks were ever attributed. v1.0.10 ships the missing piece. The script is safe to run from cron (CLI usage, supports `--dry-run` / `--batch=N` / `--max-batches=N` / `--verbose`), respects `NUMINIX_SEEKMODO_INDEX_BATCH`, and refuses to run when the connector isn't paired, mode=off, or the tenant is locked out. Doc shape mirrors the gateway commerce schema in `services/mcp-gateway/ops/tenant-add.php` (id / name / model / description / brand / category_id[] / p_type / category_breadcrumbs[] / price / in_stock / sku / url) — Phase B rerank features (is_primary, head_noun, price_pct_in_category, …) are computed gateway-side by `IndexTool::FeatureExtractor` on every upsert. The `tools/install_*_connector.py` scripts now print the matching cron line for this script in their post-install summary.

- **Suggest-dropdown click attribution.** The v1.0.9 click hook (`NOTIFY_HEADER_START_PRODUCT_INFO`) only attributed clicks whose HTTP_REFERER was the search-results page, which dropped every click from the ajax suggest dropdown — those navigations come from whatever page hosted the search bar (homepage, category page, cart) and never carry a SERP referer. v1.0.10 splits the hook into two arms: the canonical SERP click stays `surface=results` (referer must be `advanced_search_result` / `FILENAME_SEARCH`), and a new `surface=suggest` click fires when the position-map already carries the products_id but the referer is a same-host non-SERP page. Position-map population already happens for ajax_search.php because that endpoint requires `pages/search_result/header_php.php` and so fires `NOTIFY_SEARCH_RESULTS` — the new arm is purely about loosening the attribution condition, no change to the search hot path. Deep links and external-search-engine arrivals still drop both arms (no position-map entry → no click). The `surface` field flows through into the trainer's graded-label stream so SERP and suggest clicks can be valued differently in LTR.

- **Filter-mapping registry: Zen Cart core defaults.** `_numinix_seekmodo_filter_registry()` now seeds `categories_id` and its `cPath` alias as default `int → category_id` mappings, so any storefront whose SERP is bound to a category via the URL gets that constraint applied to the gateway's Typesense `filter_by` clause without having to hand-register the mapping in an init include. The legacy nmn_filters defaults (`brand`, `type`, `capacity_by_lbs`) are preserved verbatim — the Redline tenant's behavior is unchanged. `pfrom` / `pto` are intentionally NOT added to the registry because `_numinix_seekmodo_build_search_payload` already forwards them as top-level `price_from` / `price_to` payload keys + a structured `filters` entry; duplicating them in the registry would attach the price constraint twice. `manufacturers_id` is also intentionally not in the registry today — the Typesense schema's `brand` field is a string (manufacturer name) and the int manufacturer_id ride along the top-level `manufacturers_id` payload key + structured `filters` map for telemetry; bringing it into the registry would require a new `manufacturer_id` int facet on the schema, deferred to a future release.

## v1.0.9
- **Zero-touch storefront integration via Zen Cart notifier observer (Sprint 13).** New `catalog/includes/classes/observers/NuminixSeekmodoObserver.php` attaches to five core Zen Cart notifiers and replaces the previous "edit `class.search.php` by hand" integration contract for every storefront on stock Zen Cart 1.5.8 or 2.0+. Up to v1.0.8, an un-patched storefront would happily install the plugin, complete the Connect-to-Seekmodo handshake, and then **silently never call the gateway** — every search ran through native Zen Cart LIKE because no callsite invoked `numinix_seekmodo_run_search()`. v1.0.9 closes that gap by registering the observer through `auto_loaders/config.numinix_seekmodo.php` (`autoLoadConfig[200]` `class` + `classInstantiate` entries), so the swap-points fire automatically:
  - `NOTIFY_SEARCH_RESULTS` (fired from `includes/modules/pages/search_result/header_php.php` and inherited by `ajax/ajax_search.php`) — replaces the native `splitPageResults` SQL with a `SELECT ... WHERE p.products_id IN (...) ORDER BY FIELD(p.products_id, ...)` clause built from the gateway's ranked product list, and refreshes `number_of_rows` / `number_of_pages` so the Zen Cart paginator + listing template render exactly as if the gateway had been the database all along. The rewritten SQL carries a `/* numinix_seekmodo_observer */` marker so a legacy hand-patched storefront (redlinestands) that already swapped at `numinix_elastic_search_results()` is detected and the observer's swap is skipped — fully idempotent against the existing integration.
  - `NOTIFY_HEADER_END_ADVANCED_SEARCH_RESULTS` — fires a SERP impression beacon via `numinix_seekmodo_mirror_serp_impression()`, threading the gateway's `search_event_id` from the just-completed search so the trainer can join impression → search row precisely.
  - `NOTIFY_HEADER_START_PRODUCT_INFO` — fires a click beacon via `numinix_seekmodo_mirror_click()` when the shopper arrives on a product page from a SERP we just rendered. Two-pronged attribution heuristic: the per-shopper `_numinix_seekmodo_serp_positions` session map (populated by the search-results swap, capped at 250 entries) carries the products_id → 1-based rank, AND the `HTTP_REFERER` host matches the storefront's `HTTP_HOST` and the path / query references `FILENAME_SEARCH` or `main_page=advanced_search_result`. Deep links and external-search-engine arrivals do NOT generate a click.
  - `NOTIFY_CART_ADD_CART_END` — fires `numinix_seekmodo_mirror_add_to_cart()` (LTR-P6 graded label, weight 2). Reads `products_id` from `$_GET` / `$_POST`, quantity from `$_POST['cart_quantity']`.
  - `NOTIFY_CHECKOUT_PROCESS_AFTER_ORDER_CREATE_ADD_PRODUCTS` — fires once per order line item. Routed to `numinix_seekmodo_mirror_purchase()` (LTR-P6 strongest label, weight 4) with the per-line `qty` and `final_price` for the trainer's revenue-aware grading.

  Failure posture: every hook is wrapped in a `try/catch` and any exception is swallowed (logged to `logs/numinix_seekmodo.log` when `NUMINIX_SEEKMODO_DEBUG=true`). A misbehaving observer can never 500 the storefront page — same posture as the existing `numinix_seekmodo_run_search()` → null fallback contract.

- **`zcVersions` widened from `['v158']` to `['v158', 'v200']`.** The notifier observer pattern is part of Zen Cart's stable public API on both major versions, so the same plugin tree drops onto Zen Cart 1.5.8 and 2.0.x storefronts without conditional code. Tested on numinix.com (Zen Cart 2.0.1) and redlinestands.com (Zen Cart 1.5.8a) with the same observer file.

- **`tools/install_numinix_connector.py` is no longer required to patch storefront PHP.** The integration contract is "the Plugin Manager / SQL bootstrap installs the plugin tree, the auto_loader registers the observer, and the rest is automatic." Existing hand-patched storefronts (redlinestands) keep working unchanged — the observer's idempotency guard (`/* numinix_seekmodo_observer */` SQL marker probe) prevents double-swapping when both integrations are live.
